How your app checks who you are — and moves data safely

You built the screens. This explains the plumbing behind them: how TypeScript, Next.js, Clerk, and Convex pass a person's identity around, and how a click in the browser becomes a trusted answer from the database — using your real code.

The 20-second version

Clerk proves who you are and hands the browser a short-lived, tamper-proof badge (a token). Every time your app asks Convex for data, it shows that badge. Convex checks the badge is genuine, figures out which user it belongs to, and only then reads or writes the database. Next.js is the app the browser runs; TypeScript is the shared language that catches mistakes before they ship.

01

The four players (a members-club analogy)

Imagine a private training club. Four things make it run — and each maps to one piece of your stack.

🏛️

Next.js the building

Frontend framework

The club itself — the rooms, doors and signs people walk through. It renders your pages (/formations, /dashboard) and runs the React code in the browser.

🪪

Clerk the door team

Identity & login

The people at the entrance. They verify who you are, keep the member list, and clip a wristband on you that proves your identity for a short while.

🗄️

Convex the vault + staff

Database & backend logic

The back office that holds everything valuable — courses, who bought what, progress — and only acts when a request shows a valid wristband.

🧩

TypeScript the language

Typed JavaScript

The common language everyone speaks. Because it's typed, whole classes of mistakes are caught while you write, not after a user hits them.

Key idea

The browser never talks to the database directly, and it never holds any secret keys. It only ever holds a short-lived badge. Everything sensitive happens on Clerk's and Convex's servers.

03

The token — a tamper-proof ID badge

The whole system hinges on one object: a JWT (JSON Web Token). Think of it as a wristband that Clerk stamps. It's just text, but it's cryptographically signed, so Convex can tell it's genuine and hasn't been edited — without calling Clerk.

A token carries small facts called claims. Yours (from the convex template we set up) looks conceptually like this:

Why it expires so fast

The badge is valid for about 60 seconds. If someone ever stole one, it's near-useless moments later. The browser silently asks Clerk for a fresh one whenever it's needed — you never notice.

Two claims do the heavy lifting later: iss (who made the badge) and aud (who the badge is for). Remember those two — Convex checks exactly them.

05

The handshake: how Convex trusts Clerk

Clerk and Convex are run by different companies. They never call each other. So how does Convex believe a token really came from your Clerk? Two matching facts — the same iss and aud from Section 3.

On the Convex side

auth.config.ts

You told Convex: "only trust tokens issued by this exact Clerk address, made for an audience called convex."

On the Clerk side

the "convex" JWT template

You told Clerk: "when someone asks for a convex token, stamp aud: convex on it (plus email & name)."

When both sides agree, the handshake works. Convex verifies the signature, checks iss and aud match its config, and accepts the token. That's the entire trust model — no shared password, no back-channel.

The golden rule

The frontend decides what to show; the backend decides what's true. Hiding a button in React is not security — the real check always happens inside a Convex function, using the identity from the token. Never trust the browser.

Query vs. mutation — the two verbs

You'll see two words constantly. They're simple:

useQuery · read

Asks a question and keeps listening. If the underlying data changes, your component re-renders on its own. Example: hasAccess, list my courses.

useMutation · write

Performs a change once, in a safe transaction. Example: store me, record lesson progress, create a course.

Guarding whole pages before they load

Section 6 protects data. But you also want to stop a signed-out person from even opening /dashboard or /admin. That's a doorman that runs on every request, before any page renders — in Next.js it's a file called proxy.ts (older projects call it middleware.ts).

08

Owning a course: the one-time-purchase model

Your model is pay once, keep forever, per course. That makes "access" beautifully simple: a person owns a course if — and only if — there is one row linking them to it in the entitlements table.

Fig. 6 — how a purchase becomes access
%%{init: {'theme':'dark','themeVariables':{'fontFamily':'ui-monospace, monospace','primaryColor':'#12211b','primaryBorderColor':'#35c07a','lineColor':'#5f8a78','primaryTextColor':'#d8e3dc'}}}%%
flowchart LR
  BUY["Click Buy"] --> ORD["orders row · pending"]
  ORD --> PAY["Pay at Stripe"]
  PAY --> WH["Stripe webhook confirms · verified"]
  WH --> ENT["entitlements row created"]
  ENT --> ACC["hasAccess = true · video unlocks"]
  1. Start checkout. A Convex mutation creates an orders row marked pending and sends you to Stripe. The price comes from the course record on the server — never from the browser.
  2. Pay. You pay on Stripe's own page. No card details ever touch your servers.
  3. Stripe calls back. Stripe sends a signed webhook to your backend confirming the payment. This is the only thing trusted to grant access — not a "success" screen in the browser, which could be faked.
  4. Access granted. The verified webhook flips the order to paid and inserts the entitlements row. From then on, hasAccess returns true and the lesson video unlocks.
Why the webhook, not the browser

Anyone can open the "payment complete" URL directly. Only Stripe can produce a correctly-signed webhook. Granting access strictly on the webhook is what keeps the paywall real. (This is Phase 4 — the tables and rules already exist; wiring Stripe comes next.)

10

Glossary — every term, in one line

Frontend / backend
Frontend = what runs in the browser (your pages). Backend = what runs on a server you trust (Convex functions).
Component
A reusable piece of UI written in TypeScript/React, e.g. your Navbar or HeroTerminal.
"use client"
A tag at the top of a file meaning "this runs in the browser and can be interactive" (use state, clicks, Convex hooks).
Provider
A wrapper placed high in the app that makes something (login state, the Convex connection) available to everything inside it.
JWT / token
A short-lived, signed "badge" proving who you are. Readable by anyone, forgeable by no one.
Claim
One fact inside a token, e.g. email, aud, exp.
Issuer (iss)
Who created the token — your Clerk address. Convex checks it matches auth.config.ts.
Audience (aud)
Who a token is for. Yours says convex, which is why the convex JWT template exists.
Query
A Convex read that keeps your UI live — it re-renders when data changes.
Mutation
A Convex write that changes data once, safely, in a transaction.
Schema
The definition of your tables and fields (convex/schema.ts). TypeScript enforces it everywhere.
Entitlement
A row saying "this user owns this course." Its existence is the access check.
Middleware / proxy
Code that runs on every request before a page loads — your page doorman (proxy.ts).
Webhook
A signed server-to-server message (e.g. Stripe → you) confirming an event actually happened.
Environment variable
A setting kept out of code, in .env.local. NEXT_PUBLIC_ ones are safe for the browser; the rest are secret.
SSR & hydration
Next.js builds the page's HTML on the server first (fast first paint), then React "wakes it up" in the browser. A "hydration mismatch" just means the two versions differed — often a browser extension (like Google Translate) editing the page.
